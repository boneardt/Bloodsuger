# Bloodsuger

A self-hosted PHP app for tracking blood glucose readings: upload Contour meter CSV exports, view color-coded readings and rolling averages, export a PDF report. See `README.md` for setup/deployment steps.

## Stack & constraints

- **Plain PHP 8.1+, no framework, no build step, no Composer.** One `.php` file per page at the project root (`index.php`, `login.php`, `logout.php`, `setup.php`, `import.php`, `settings.php`, `logins.php`, `sync_health.php`, `sync_csv.php`, `export_pdf.php`, `forbidden.php`); shared logic in `includes/`.
- **SQLite via PDO** (`data/bloodsuger.sqlite`, gitignored, created automatically at first request by `includes/db.php`). No MySQL.
- **Designed for typical low-cost shared PHP hosting, FTP-only access assumed (no SSH/Composer required).** This is why there's no Composer — the PDF library (`vendor/tfpdf/`) was downloaded directly from its GitHub source and vendored as plain files. (The original deployment this was built for was IONOS shared hosting specifically, but nothing in the code assumes that host.)
- **The app may be deployed at the domain root or in any subdirectory.** Every internal link/redirect/asset path MUST go through `bs_url()` / `bs_asset()` (in `includes/helpers.php`), never a hardcoded leading `/`. These auto-detect the base path from `$_SERVER['SCRIPT_NAME']`, so the same codebase works unmodified wherever it's uploaded.
- **No local PHP or Node available in the dev environment this was built in.** Code has only been manually reviewed, never executed. Test with `php -S localhost:8000` (or on the real hosting target) before trusting changes — don't assume correctness from review alone.

## Key decisions (the "why" isn't obvious from the code alone)

- **Threshold model is 4 boundaries (bands), not a single cutoff.** `value < A` → red (too low), `A–B` → yellow, `B–C` → green, `C–D` → yellow, `> D` → red (too high). This came from a real clinic whiteboard showing different targets for fasting (4–7) vs. post-meal (8–10) — glucose has danger at both ends, so a single red/green split isn't clinically right. Logic lives in `includes/color_classifier.php` (`bs_classify_detail()`).
- **Status is never color-only — user is colorblind.** Every status indicator (badges, chips, average-card border, PDF status column) pairs its color with a distinct icon (▼▽✓△▲) and an explicit text label (Low / Borderline low / In range / Borderline high / High), never relying on hue alone. The PDF table has a text status-code column (L/BL/OK/BH/H) alongside the color swatch for the same reason.
- **Status colors are fixed exact values, not theme-derived tints**: red `#ff0000`, yellow `#ffff00`, green `#008000`, defined once in `:root` in `assets/css/style.css` and used identically in light and dark mode. Each pairs with a `-contrast` text color chosen for readability — importantly, **pure yellow text on the page background is nearly unreadable**, so status is always shown as a solid-fill chip/badge/border with contrasting text (white on red/green, black on yellow), never as raw colored text sitting directly on the page background.
- **Login throttling is stored in SQLite (`login_attempts` table), not in-memory.** Shared hosting may route requests to different PHP worker processes, so an in-memory rate limiter wouldn't actually work.
- **Login audit trail**: every successful and failed login is written to the `login_log` table (username as typed, IP, time — never the password) and shown on the admin-only `logins.php`. Pruned to the newest 1000 rows in `bs_log_login()`. Throttled attempts aren't logged. Separate from `login_attempts`, which is only for rate limiting.
- **Account management (Settings → Accounts)**: admins can change any account's password and delete any account, inline in the accounts table (`settings.php`, `includes/auth.php`: `bs_update_password()`, `bs_delete_user()`, `bs_count_admins()`). Deleting is blocked for your own currently-logged-in account and for the last remaining admin — both checked server-side in `settings.php`'s `delete_user` branch, not just hidden in the UI.
- **Setup wizard only creates the admin account.** The remaining accounts (up to `BS_MAX_USERS = 4` total, in `includes/auth.php`) are added later from the Settings page's "Accounts" section, not during first-run setup.
- **CSV import upserts on the parsed timestamp** (unique column on `measurements.timestamp`), matching the Contour export's `DD.MM.YYYY HH.MM.SS` format. Re-importing the same file is idempotent (reports "updated", not "added" again). Bad rows are skipped with a reason, never abort the whole batch — see `includes/csv_import.php`.
- **Passwords**: `password_hash()` with Argon2id if the PHP build supports it, falling back to bcrypt (cost from `config.php`). Never stored or logged in plaintext anywhere.
- **PDF fonts**: `vendor/tfpdf/` bundles DejaVu Sans TTFs specifically for correct æ/ø/å rendering (the source CSV notes are in Danish). Don't swap in a font without checking Unicode coverage.
- **Dashboard row icons** (`index.php`, each row's summary button): Activity (🏃) and Location/`Land` (📍) are shown next to the existing Notes (💬) icon, in that order, to the left of the value badge. All three share one `.row-icon` CSS class/hover-tooltip rule (`assets/css/style.css`) instead of duplicating it — reuse this class for any future per-row icon rather than adding a new one-off style. Tap-to-reveal works for free because the icons sit inside `.measurement-row__summary`, whose existing click handler (`assets/js/dashboard.js`) already expands the whole row's detail panel.
- **Selected-period average** (`index.php`'s hidden `#period-average-card`, computed in `assets/js/dashboard.js`): when a from/to date filter is active, a 5th average card shows the average of the currently visible (filtered) rows, with the same colored border + icon/label badge as the other average cards. This requires a **JS copy of the threshold band logic** (`classify()` in `dashboard.js`, fed via `data-threshold-*` attributes on the card) that mirrors `includes/color_classifier.php`'s `bs_classify_detail()` exactly — if the band model or its boundaries ever change shape, update both places.
- **Two Shortcut-driven sync endpoints, both reusing the same token.** Neither is a browser client, so neither uses a session/CSRF — both are gated by `bs_require_sync_token()` (`includes/helpers.php`), checking a single long random shared secret (`settings.sync_token`, shown/regenerable together for both endpoints in Settings) with `hash_equals()`. This exists because the meter (Contour Plus Blue) has no public sync API and its Bluetooth protocol isn't documented — both endpoints sidestep that by reading from data the Contour Diabetes app *already* writes somewhere else via its own official integrations, rather than talking to the meter at all.
  - **`sync_csv.php`** — the richer of the two in theory: same `bs_validate_csv_upload()`/`bs_import_csv()` reuse as the manual Import CSV page, so it would get every field (notes, activity, meal marker, etc.) if fed the real CSV. `bs_validate_csv_upload()` takes a `$requireCsvExtension` flag (default `true`) because of this path: iOS Shortcuts' "Get Contents of URL" file-type form field doesn't reliably preserve the ".csv" extension on the filename it sends, even though the file content is fine — confirmed empirically. `import.php`'s browser form keeps the default `true`.
  - **Known limitation, confirmed by extensive testing: Contour's Share Sheet action cannot be wired directly to `sync_csv.php` one-tap.** Contour's "Share" on its Raw Data (csv) report hands a *compound* payload to third-party Share Sheet extensions — an auto-generated Danish cover-note (as a `.txt`-named attachment) *and* the real CSV — but a custom Action Extension (which is what a Shortcut set up for the Share Sheet is) only ever receives the cover-note, never the CSV, no matter how the Shortcut is configured (tried: unrestricted receive, restricted to Files, explicit `Filtrer filer` on filename ending `.csv`, and an internal `Gem fil`/Save-File step — all four returned byte-identical wrong content). Only privileged consumers (Mail, the system's own "Gem i Arkiver"/Save to Files) appear to get the real attachment; this is Contour/iOS behavior, not something fixable from the Shortcut side. Two working alternatives exist instead (README "Automated sync" section, Options A and C) — don't re-attempt one-tap-from-Contour without new evidence that Contour's share behavior has changed.
  - **The most-automatic option (README Option C) is a `launchd` `WatchPaths` agent on a Mac**, not an iOS Shortcut at all: an iCloud-synced folder gets watched, and the newest `ContourCSVReport*.csv` in it (deliberately not just any `*.csv` — the same folder can hold unrelated exports, e.g. from MedM) gets POSTed to `sync_csv.php`. The one easy-to-lose gotcha: a script launched by `launchd` (not from an interactive Terminal session) does **not** inherit the same access to `~/Documents` that an interactive session has — macOS's privacy protections block it *silently* (no error, the glob just finds nothing, as if the folder were empty) unless Full Disk Access is granted explicitly to `/bin/bash` in System Settings. Confirmed by direct A/B testing: identical script, interactive runs succeeded immediately, `launchd`-triggered runs failed every time until that permission was granted.
  - **`tools/mac-agent/install.sh` + `uninstall.sh`** package the above into a reusable installer for other self-hosters, not just this one Mac. It's a plain script users `git clone` and run themselves, deliberately **not** a curl-pipe-to-bash one-liner — it ends up with Full Disk Access, so letting people read it first via a normal clone is the safer, more transparent distribution method, and also sidesteps ever needing to hardcode a public raw-GitHub URL. The generated `~/.config/bloodsuger/config` values must be quoted when written, since `sync.sh` later `source`s this file and an unquoted space in a folder path (e.g. "Diabetes forbedring") gets parsed as a second shell command, not part of the value. **Don't use `printf '%q'` for this** — it was tried first and seemed to work, but its escaping of non-ASCII bytes (an "å"/"ø" in a folder name) depends on the shell's locale at the moment the installer runs, and silently mangled the character on a second real run under a different locale than the one that happened to work during initial testing. The fix in place now is a plain `quote_for_config()` helper that wraps values in single quotes itself (escaping any embedded `'` the standard POSIX way) — locale-independent, byte-for-byte, no shell escaping logic to get subtly wrong. Both bugs (the original unquoted-space one and this locale-dependent one) were found only by actually running the installer end-to-end with a real non-ASCII folder path, not by reading the code — re-verify the same way after touching this file, and don't reintroduce `%q` here.
  - **`sync.sh` retries the upload** (up to 4 attempts, 5s apart, plus an initial 3s delay before the first try) instead of a single curl call. Found by real-world testing on the live agent, not anticipated upfront: `launchd`'s `WatchPaths` can fire the instant iCloud *starts* writing a file into the watched folder, before it's fully downloaded to the Mac — the first attempt reading/uploading it can genuinely fail (`HTTP_STATUS:000`, empty response) for a file that's completely fine moments later. A single-attempt script looks "broken" intermittently for a reason that has nothing to do with the token, Full Disk Access, or the server. Keep this retry loop if touching `sync.sh` again — don't simplify it back to one curl call.
  - **`sync_health.php`** — reads Blood Glucose samples Apple Health already has (because the Contour app shares them there). Request body is plain form fields (`timestamp`, `value`), deliberately **not JSON** — hand-building JSON strings inside iOS Shortcuts is fragile (unescaped newlines break it); responses are plain text for the same reason. Captures far less than the CSV path (no notes/activity — HealthKit's Blood Glucose type isn't designed to carry those), kept as a lighter alternative for anyone who hasn't got/wants the CSV route.
  - Both upsert by timestamp (`sync_health.php` calls the shared `bs_upsert_measurement()` in `includes/csv_import.php`, extracted from `bs_import_csv()`'s former inline insert/update SQL specifically so both share it), which is what lets either Shortcut stay fully stateless — no "last synced" tracking needed, since resending unchanged readings is harmless. `sync_health.php` rows get `data_source = 'Apple Health'`; `sync_csv.php` rows get whatever `data_source` column the CSV itself specifies, same as a manual import.
- **Explicit server timezone** (`config.php`'s `timezone`, applied once via `date_default_timezone_set()` in `bs_config()`, `includes/db.php`): needed for the Apple Health sync to convert an ISO8601 timestamp-with-offset into this app's naive-local storage format correctly — and incidentally fixes a latent bug, since `includes/aggregates.php`'s rolling-average cutoffs relied on PHP's ini-default timezone (often UTC on shared hosts) before this was added.
- **Base font size is one root declaration**: `html { font-size: 15px; }` in `assets/css/style.css`. Every other `font-size` in that file is `rem`/`em`, so this is the single place that scales all text on the site together — don't add a new hardcoded `px` font-size elsewhere, or it won't scale with the rest.

## Deploying

SFTP deploy is set up via the `ionos-sftp` skill: `.ionos-deploy.json` (committed, no secrets) points at `/web/Bloodsuger` on the IONOS account shared with other projects on this machine (same SFTP key/login as e.g. StockNews, different folder). Use:

```
python3 ~/.claude/skills/ionos-sftp/sync.py status   # diff local vs. server
python3 ~/.claude/skills/ionos-sftp/sync.py push      # upload new/changed files
python3 ~/.claude/skills/ionos-sftp/sync.py check     # verify the live URL checks
```

`data/bloodsuger.sqlite*` is explicitly in the config's `skip` list — the live database is never touched by `push`. `push --delete` and the skill's `clean` command need the user's explicit go-ahead first (per the skill's own rule), same bar as any other destructive action.

Checked empirically (see `check`'s results): the skill's general warning that `Require`/`FilesMatch` directives in `.htaccess` commonly cause 500 errors on IONOS does **not** hold on this account — the existing `.htaccess` files (`data/`, `includes/`, `vendor/`, root) correctly return `403`, not `500`. Don't preemptively "fix" these to the `RewriteRule ^ - [F]` pattern the skill recommends elsewhere; they're confirmed working as-is here.

## Live deployment — protect the data

Whoever is running this may already have a deployment with real data in it. When telling them what to upload for an update:

- **Never overwrite `data/` (contains `bloodsuger.sqlite` and possibly `-wal`/`-shm`) or the server's `config.php`.** The server's `config.php` differs from the local dev one (`cookie_secure` is `true` there).
- Safe to overwrite: root `*.php` pages, `includes/`, `assets/`, root `.htaccess`, `config.sample.php`. `vendor/` only changes if tFPDF is touched. `tools/mac-agent/` is never deployed to the server at all — it runs locally on whoever's own Mac wants the auto-sync agent, entirely separate from the PHP app.
- Schema changes must be additive and idempotent (`CREATE TABLE IF NOT EXISTS` in `bs_migrate()` in `includes/db.php`), because it runs against the existing live database on every request. Never write a migration that drops or rewrites existing tables without an explicit backup step.
- Remind the user to download `data/bloodsuger.sqlite` before any risky update.

## Things to double check before shipping a change

- Any new page/link must use `bs_url()`/`bs_asset()` — grep for hardcoded `href="/`, `action="/`, `src="/"` or `header('Location: /` before committing.
- Any new form that mutates state needs `bs_csrf_field()` + `bs_csrf_verify()`.
- Any admin-only route needs `bs_require_admin()` (not just hiding the nav link) — read-only accounts must be blocked server-side.
